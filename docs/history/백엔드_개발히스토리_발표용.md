## 1. 약 스캔: 사진 한 장 → 약 정보

### 1-1. OCR이 약 이름을 틀리게 읽는다 ⭐ 대표 사례
- **문제**: 실제 약봉투 사진을 CLOVA OCR로 읽으면 `씨프로바이정` → `세프로바이정`, `밀리그램` → `일리그럼`처럼 오타가 생겼습니다. 함량이 잘리기도 했습니다. 처음 만든 검색은 이름이 완전히 같아야 해서 하나도 찾지 못했습니다.
- **1차 해결 (44b9d56)**: 공백·단위·괄호 성분명을 정규화하고, 문자 유사도 검색을 붙였습니다. 함량·제형이 같은 후보를 먼저 보여 줍니다. 그래도 유사도만으로는 "비슷한 다른 약"을 골라 버릴 위험이 남았습니다.
- **2차 해결 (79ff5b5)**:
  - 식약처 허가 품목을 전부 수집하는 collector를 만들었습니다. 페이지마다 체크포인트를 남겨, 중간에 끊겨도 이어서 받습니다.
  - 수집한 데이터로 **약 이름 사전 42,725개**를 만들었습니다.
  - OCR 문장에서 사전에 있는 이름을 찾아 후보로 씁니다. 다만 4만 개 사전에서는 세 글자 단어 대부분이 어딘가에 걸리므로, 사전에 걸렸다는 것만으로는 후보로 인정하지 않습니다.
  - **봉투 문구와 교차 확인**: 이름이 오타일 때는 봉투에 적힌 효능 문구(예: "항생제", "세균에 의한…")를 공식 효능과 비교합니다. 둘이 맞을 때만 그 약으로 확정합니다.
  - 효능이 다르거나, 비슷한 후보가 둘 이상이면 확정하지 않고 "불확실"로 남깁니다.
- **결과**: 오타가 난 약도 근거가 있을 때만 식별합니다. 허가 상태(취하, 유효기간만료)도 함께 안내합니다.
- **발표 포인트**: "OCR을 고치는" 대신 **공식 사전 + 봉투의 다른 단서로 검증**하는 방향을 택했습니다.

### 1-2. 금액·안내 문구까지 약으로 인식했다 (회귀)
- **문제**: 새 의약품 모듈로 바꾼 뒤 `약제비총액`·`총수납금액` 같은 금액 문구와 "해열제 시럽은 라벨대로…" 같은 안내문까지 약 후보로 뽑혔습니다. 함량이 잘리고, 전에는 찾던 부스코판도 놓쳤습니다.
- **해결 (44b9d56 → 79ff5b5)**:
  - 약 이름이 단독으로 있는 줄만 후보로 씁니다.
  - 처방전 줄 형식(`1. 가상정500mg`, `[1]약정 1정 3회 3일`, `500mg 1 3 3`)에서 복용 숫자 열을 떼어 냅니다.
  - 넓은 검색에서 잘린 결과는 식별에 쓰지 않습니다. 정확한 이름으로 다시 조회한 결과만 씁니다.
- **결과(같은 샘플)**: 원문 후보 9개 → 약 이름 5개, 식별 1개 → 2개로 복구했습니다.

### 1-3. 한 약 때문에 전체가 실패했다
- **문제**: 약 하나를 못 찾거나 DUR 정보가 비면 응답 전체가 보류됐습니다. AI 설명 검증이 원문 전체 일치를 요구해서, 자연스러운 설명은 계속 탈락했습니다.
- **해결 (44b9d56)**:
  - 약마다 결과를 따로 냅니다(판별 / 불확실).
  - 효능은 "요약 문장 + 출처 ID" 구조로 검증합니다.
  - AI 요약이 실패하면 공식 원문을 대신 보여 줍니다.
- **결과**: 찾은 약은 항상 안내합니다. AI가 실패해도 공식 정보는 나갑니다.

### 1-4. 개발자용 데이터가 사용자 화면을 덮었다
- **문제**: 응답에 원문·출처·DUR 원본이 가득해서 정작 읽을 설명이 묻혔습니다. 공식 원문에는 `<p>`, `&nbsp;` 같은 HTML이 섞여 있었습니다.
- **해결**:
  - 약 카드를 5항목으로 바꿨습니다: 효능 / 복용법 / 주의사항 / 부작용 / 보관 (44b9d56).
  - 주의사항은 CLOVA로 쉬운 문장으로 바꿉니다. 실패하면 원문을 그대로 씁니다.
  - HTML 태그를 줄바꿈이 있는 평문으로 바꿨습니다 (dbdd3a9).

### 1-5. 느렸다
- **해결 (ea5459c)**: 식약처 조회는 서로 독립이라 4개씩 병렬로 부릅니다. 같은 효능 문구를 CLOVA로 두 번 요약하던 호출 하나를 없앴습니다.
- ⚠️ 같은 입력으로 전후를 측정한 기록은 없습니다. 수치는 발표하지 않습니다.

## 2. 증상 문진: 대화 → 의심 질환·진료과

### 2-1. AI 연결부터 막혔다
- **문제**: Gemini 호출이 502로 실패했습니다. 원인은 두 가지였습니다. 스키마의 `additionalProperties`를 지원하지 않아 400이 났고, 쓰려던 모델이 신규 계정에는 제공되지 않아 404가 났습니다.
- **해결 (d097b5c)**: 전송 스키마에서 해당 필드만 빼고, 서버 쪽 Pydantic 검증은 그대로 유지했습니다.

### 2-2. 문진은 끝났는데 분석은 "정보 부족"
- **문제**: 필수 항목이 다 채워져 문진이 끝나도 분석 결과는 정보 부족으로 나왔습니다. "묵직하다" 같은 표현은 증상 필드에 없어서 분석에 전달되지 않았습니다.
- **해결 (44b9d56)**:
  - 분석에 대화 전체와 누적 증상을 넘깁니다.
  - 정보가 부족하면 추가로 질문하고, 최대 5턴에서 끝냅니다.
  - 응답 형식을 하나로 통일했습니다(`ASK_FOLLOW_UP` / `COMPLETE`).

### 2-3. 재전송·동시 요청에 대화가 꼬였다
- **해결 (d097b5c)**:
  - 메시지마다 `client_message_id`를 붙여, 같은 요청이 다시 와도 한 번만 처리합니다.
  - Redis 잠금으로 동시 요청을 막습니다.
  - 세션 TTL은 30분입니다.
  - 테스트 중 생긴 409는 Swagger가 기본 UUID를 재사용했기 때문이었습니다.

### 2-4. 문진 엔진 교체 (Gemini → CLOVA)
- **변경 (ea5459c, df1c8d9)**: 팀원이 만든 CLOVA 문진 엔진(hosAI)을 어댑터 파일 하나로 연결했습니다. 프론트와의 API 계약은 바꾸지 않았습니다. 응급 상황은 `EMERGENCY` 상태로 따로 내보냅니다. 이후 Gemini 코드는 삭제했습니다.

### 2-5. AI가 사용자가 말하지 않은 증상을 이유로 댔다 ⭐
- **문제**: 분석 이유에 "공복 시 통증", "야간 통증"처럼 사용자가 말한 적 없는 내용이 사실처럼 들어갔습니다. 참고 문서의 내용이 섞여 들어간 것입니다.
- **해결 (ea5459c)**:
  - 프롬프트에 "말하지 않은 특징을 환자 사실처럼 쓰지 말라"는 규칙을 넣었습니다.
  - 사후 필터도 붙였습니다. 이유 문장에 사용자가 말하지 않은 임상 단서(공복·야간·발열·출혈 등)가 있으면 그 문장을 지웁니다.
- **한계**: "열은 없어요" 같은 부정 표현은 구분하지 못합니다.

### 2-6. 너무 일찍 끝나서 진료과가 틀렸다
- **문제**: LLM이 핵심 항목이 차기 전에 대화를 끝내곤 했습니다. "배가 아파요"처럼 넓은 부위나 나이를 모르는 상태에서는 진료과가 갈립니다(예: 소아청소년과 / 내과).
- **해결 (dbdd3a9)**:
  - 대화를 끝낼지는 서버가 정합니다. LLM의 이른 종료는 무시합니다.
  - 부위가 넓으면 상세 위치를 한 번 더 묻습니다.
  - 나이에 따라 진료과가 갈리는 증상이면 나이를 묻습니다.

### 2-7. 실패해도 원인을 알 수 없었다
- **해결 (45afeb9)**: 문진 실패를 종류별로 로그에 남깁니다(엔진 규칙 위반 / 출력 필드 오류 / 예외). 로그에는 세션 ID와 실패 종류만 남기고, **사용자 대화 내용은 기록하지 않습니다**.

## 3. 병원 검색: 진료과 → 주변 병원

### 3-1. 데모 데이터 → 실제 API
- **변경 (ea5459c)**: 국립중앙의료원 API로 교체했습니다. 반경, 진료 중 여부, 진료시간을 제공합니다. 좌표는 NCP 지도로 시·구 이름으로 바꿉니다.

### 3-2. 문진이 추천한 진료과로 병원이 안 나왔다
- **문제**: 문진은 "소화기내과"를 추천하는데, 병원 API가 받는 진료과 이름은 "내과"였습니다.
- **해결 (dbdd3a9)**: 추천 진료과를 병원 검색의 표준 이름으로 바꿔서 내보냅니다.

### 3-3. 호출 한도를 넘으면 엉뚱한 에러가 났다 ⭐
- **문제**: 공공 API는 한도를 넘으면 정상 응답 형식이 아닌 게이트웨이 코드(`returnReasonCode=22`)를 돌려줍니다. 서버가 이를 오류로 인식하지 못했습니다. 요일 조건까지 캐시 키에 들어가 있어서 캐시도 거의 맞지 않았습니다.
- **해결 (dbdd3a9)**:
  - 한도 초과를 감지해 `429 RATE_LIMIT_EXCEEDED`로 응답합니다.
  - 요일 조건 없이 진료시간 원본만 1시간 캐시합니다. 진료 중 여부는 요청마다 다시 계산합니다.
- **결과**: 외부 호출이 줄고, 한도 초과도 명확한 에러로 보입니다.

### 3-4. 진료과를 하나밖에 못 찾았다
- **해결 (dbdd3a9)**:
  - `내과,외과`처럼 여러 진료과를 받습니다(최대 5개, 호출 한도 보호).
  - 진료과 × 지역 조회를 병렬로 부릅니다.
  - 진료과마다 상한을 둬서 한 과가 결과를 독차지하지 않게 했습니다.
  - 진료 중인 병원을 먼저 보여 줍니다.

- **코드 정리 (df1c8d9)**: 교체된 Gemini, 구 약 서비스, 데모 데이터 등 약 1,000줄을 삭제했습니다.
- **테스트 (ea5459c~)**: 테스트는 로컬에만 둡니다(git 제외). CI는 ruff 검사만 합니다.

## 발표에 쓸 때 주의

- 정확도·인식률은 따로 측정하지 않았습니다. 수치는 **특정 샘플의 전후 비교**로만 말합니다(후보 9→5, 식별 1→2).
- AI 요약이 실패해 공식 원문을 보여 준 경우를 "AI 요약 성공"으로 세지 않습니다.
- 속도 개선은 전후 측정이 없습니다. 방법만 설명합니다.
- 의료적 정확성은 검증하지 않았습니다. 시연용 서비스입니다.

## 추천 슬라이드 흐름 (대표 사례 3개)

1. 서비스 흐름: 문진 → 진료과 → 병원 / 약 사진 → 약 정보
2. 구조: FastAPI + Redis, AI는 어댑터로 교체 가능(실제로 Gemini → CLOVA 교체)
3. ⭐ OCR 오타 → 유사도 검색 → 약 사전 42,725개 + 봉투 효능 교차 확인 (1-1, 1-2)
4. ⭐ AI가 말하지 않은 증상을 지어냄 → 프롬프트 규칙 + 사후 필터 (2-5)
5. ⭐ 공공 API 호출 한도·진료과 이름 불일치 (3-2, 3-3)
6. 실패 처리 원칙: 약별 부분 결과, 원문 fallback, 확실하지 않으면 보류
7. 배포와 남은 과제: KDCA API 연동, 부정 표현 처리, 속도 측정
