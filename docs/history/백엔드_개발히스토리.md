# MediNavi 백엔드 주요 개선 히스토리

정리 범위: 2026-11-20~2026-11-25. 기존 개발 기록을 바탕으로 RAG 검색, OCR 약품 식별, 약 설명 형식, 다중 진료과 검색의 변경 과정을 정리했다.

## 1. 문진 RAG: 실시간 검색에서 FAISS 인덱스로

### 1-1. 기존 검색 방식

초기에는 분석 요청이 들어올 때마다 MedlinePlus 검색 API에서 최대 6개 문서를 가져왔다. 질문과 검색된 문서를 각각 임베딩한 뒤 관련 문서를 골라 분석에 전달했다.

```text
분석 요청 → MedlinePlus 실시간 검색 → 질문·검색 문서 임베딩
         → 관련 문서 선택 → 분석에 참고 자료 전달
```

요청 한 건에 임베딩 호출이 최대 7회 필요했다. 동일한 문서가 다시 검색돼도 임베딩을 반복했으며, 참고 자료 후보도 검색 API가 반환한 문서로 제한됐다.

### 1-2. 참고 문서 사전 수집

요청 처리와 문서 준비 과정을 분리했다. MedlinePlus 공식 영문 건강 주제 XML에서 1,017개 문서를 확보하고, 검색에 사용할 문서 집합을 미리 구성했다.

실시간 검색 결과 몇 개 안에서 고르는 구조에서, 수록한 전체 문서 중 관련 자료를 찾는 구조로 검색 범위를 바꾼 것이다.

### 1-3. 임베딩과 FAISS 인덱스 구축

수집한 문서는 CLOVA 임베딩(bge-m3)으로 미리 벡터화하고 FAISS 인덱스에 저장했다. 문서 벡터를 요청마다 다시 만들지 않고 재사용하도록 했다.

```text
사전 준비: MedlinePlus 문서 수집 → 문서 임베딩 → FAISS 인덱스 저장
요청 처리: 질문 임베딩 → 인덱스 유사도 검색 → 상위 3개 문서 → 분석
```

정상적인 인덱스 검색 경로에서는 질문만 임베딩한다. 코사인 유사도로 상위 3개 문서를 선택하며, 인덱스가 없거나 검색에 실패하면 기존 실시간 검색으로 전환한다.

### 1-4. 변경 결과

| 항목 | 기존 | 변경 후 |
|---|---|---|
| 문서 준비 | 요청마다 실시간 검색 | 전체 문서 사전 수집·인덱싱 |
| 검색 후보 | 검색 API가 반환한 최대 6개 | 인덱스에 수록한 1,017개 |
| 요청당 임베딩 | 최대 7회 | 정상 인덱스 경로에서 1회 |
| 분석에 전달할 자료 | 실시간 검색 결과에서 선택 | 유사도 상위 3개 선택 |
| 인덱스 사용 불가 시 | 해당 없음 | 실시간 검색으로 전환 |
| 문서 검색 시간 (평균) | 2,084ms | 133ms (FAISS 검색 자체는 1ms) |

검색 시간은 증상 예시 3개를 각각 2번씩, 로컬 Docker에서 잰 값이다. 검색 단계만 잰 것이며, 검색어 생성·제목 번역·최종 분석 같은 LLM 호출은 포함하지 않는다. 기존 방식은 편두통 예시에서 검색 후보가 2건뿐이었다.

## 2. OCR 오타 대응과 약 이름 사전 구축

### 2-1. 실제 약봉투에서 드러난 문제

OCR로 읽은 텍스트를 의약품 분석에 연결했지만, 약 이름이 틀리면 공식 품목 검색부터 실패했다. 약 이름과 함량이 붙거나 일부가 잘리는 문제도 있었다.

| 원래 표기 | 관찰된 OCR 표기 | 식별에 미치는 영향 |
|---|---|---|
| 씨프로바이정 | 세프로바이정 | 정확한 이름 검색에서 누락 |
| 밀리그램 | 일리그럼 | 함량 단위 해석에 방해 |
| 약 이름과 함량 | 일부 잘림·붙여 읽기 | 유사 품목 구분이 어려워짐 |

핵심 문제는 읽힌 문장을 자연스럽게 설명하는 능력보다, 오타가 있는 이름을 실제 공식 품목에 연결하는 과정이었다.

### 2-2. AI 추정과 검증 조건 조정

초기에는 AI가 비슷한 약 이름을 후보로 제안하도록 프롬프트를 보완하고, 응답 형식과 검증 조건을 조정했다. 검증이 지나치게 엄격하면 활용 가능한 응답까지 보류됐지만, 조건을 완화하는 것만으로 오타가 있는 이름의 품목을 확정할 수는 없었다.

이에 약 이름 후보를 찾는 과정과, 실제 품목으로 확인하는 과정을 구분했다. AI의 추정 결과를 확인할 공식 이름 목록과 검색 근거가 필요했다.

### 2-3. 문자 정규화와 유사도 검색

공백·단위·괄호 표기를 정규화하고, 문자 유사도로 가까운 약 이름을 탐색하도록 했다. 함량과 제형이 맞는 후보를 우선하도록 보완했다.

이 단계에서는 오타 때문에 정확한 검색에서 빠지던 이름도 후보로 찾을 수 있었다. 다만 유사한 이름의 다른 약이 함께 나올 수 있어, 유사도 점수만으로 품목을 확정하지 않도록 했다.

### 2-4. 식약처 약 이름 사전 42,725개 구축

반복적인 AI 추정 조정에 더해, 식약처 허가 품목을 수집하는 수집기를 만들었다. 수집 결과를 바탕으로 기록 당시 42,725개 약 이름 사전을 구성했다.

수집기는 페이지별 체크포인트를 저장한다. 외부 API 오류나 중단이 발생해도 처음부터 다시 받지 않고 진행 지점부터 재개할 수 있도록 했다.

```text
식약처 허가 품목 수집 → 약 이름 사전 구축
                              ↓
OCR 표기 → 정규화·문자 유사도 → 공식 이름 후보 탐색 → 품목 확인
```

사전은 OCR 결과를 대조할 공식 이름의 기준이 됐다. 개별 오타를 약 이름별로 하드코딩하는 대신, 수집한 이름 목록을 활용해 후보를 찾도록 발전시켰다. 약품 식별에는 문자 유사도와 사전을 사용했으며, 벡터 DB는 도입하지 않았다.

오타 입력으로 여러 약 후보를 비교하는 예시(현재 사전 검색 함수의 실제 실행 결과):

**입력: `타이래놀정500밀리그램`**

| 사전에서 검색된 후보 | 이름 유사도 | 함량 비교 | 제형 비교 |
|---|---|---|---|
| 타이레놀정500밀리그람 | 75% | 일치 | 일치 |
| 타이레놀8시간이알서방정 | 75% | 비교 불가 | 비교 불가 |
| 타이레놀산500밀리그램 | 75% | 일치 | 불일치 |

표에서는 공식 이름의 괄호 안 성분명을 생략했다. 유사도는 이름 어간의 문자 비교 점수이며, 해당 약일 확률은 아니다. ‘비교 불가’는 현재 함수가 비교할 값을 추출하지 못한 경우다.

```text
OCR 오타 입력: 타이래놀정500밀리그램
                    ↓
사전에서 비슷한 이름의 약 후보 여러 개 검색
                    ↓
이름 유사도와 함량·제형 비교
                    ↓
타이레놀정500밀리그람을 가장 타당한 오타 후보로 추정
```

세 후보의 이름 유사도는 같지만, 입력의 500mg·정제 조건까지 일치하는 첫 번째 후보를 우선할 수 있다. 이 예시는 사전 후보 검색·비교 결과이며, 최종 품목 식별 완료를 뜻하지 않는다.

### 2-5. 사전 후보에 추가 단서 결합

큰 사전에서는 짧은 일반 문구도 약 이름과 비슷하게 걸릴 수 있다. 따라서 사전에서 후보를 찾았다는 사실만으로 식별을 완료하지 않았다.

- **함량·제형:** 비슷한 이름이라도 함량이나 제형이 충돌하는지 확인한다.
- **봉투 효능 문구:** ‘항생제’, ‘세균에 의한 감염’ 같은 단서를 공식 효능과 비교한다.
- **공식 검색 결과:** 넓은 검색 결과가 잘렸다면 전체 이름으로 다시 조회한다.
- **품목 상태:** 취하·유효기간만료 등의 상태를 확인한다.

단서가 충돌하거나 후보를 하나로 좁힐 수 없으면 불확실하게 남겼다. 오타 문자열을 특정 약으로 무조건 치환하는 방식은 피했다.

**주요 변화:** AI 프롬프트·검증 조건 조정에서 시작해, 문자 유사도 검색을 거쳐 공식 약 이름 사전과 추가 단서를 활용하는 식별 흐름으로 발전했다.

## 3. 약 설명을 다섯 항목으로 구분

약 설명을 하나의 긴 원문으로 전달하면 사용자가 필요한 정보를 찾기 어려웠다. 약 하나의 설명을 다음 다섯 항목으로 나눠 앱에서 일정한 형태로 보여 주도록 했다.

| 항목 | DTO 필드 | 설명 내용 |
|---|---|---|
| 약의 역할 | `purpose` | 어떤 증상에 사용하는 약인지 |
| 복용 방법 | `how_to_take` | 확인된 용법과 복용 시 주의점 |
| 복용 주의사항 | `precautions` | 질환·다른 약·음식·음주·운전 관련 주의점 |
| 이상 증상과 대처 | `side_effects` | 나타날 수 있는 증상과 전문가에게 확인해야 하는 경우 |
| 보관 방법 | `storage` | 공식 자료에서 확인된 보관 조건 |

공식 자료의 HTML은 평문으로 정리하고, 주의사항은 AI가 비전문가도 이해하기 쉬운 문장으로 다듬도록 했다. 변환이 실패하면 원문을 유지한다.

각 항목은 문자열 또는 `null`로 반환한다. 실제 처방이 확인되지 않으면 개인별 용량·횟수·기간을 추측하지 않는다. 쉬운 표현으로 바꾸면서도 원문의 조건과 주의점이 유지되는지는 추가 확인이 필요하다.

## 4. 병원 다중 진료과 검색

문진에서 여러 진료과를 추천할 수 있으므로, 병원 검색도 한 진료과만 받던 방식에서 최대 5개 진료과를 함께 받도록 확장했다.

진료과별 조회를 병렬 처리하고 결과 상한을 나눠 한 진료과의 병원만 목록에 몰리는 것을 줄였다. 이를 통해 여러 추천 진료과에 해당하는 병원을 한 번의 검색에서 확인할 수 있도록 했다.

## 5. HTTPS 배포: Caddy 리버스 프록시

처음 배포는 Uvicorn이 `http://101.79.27.212:8000`으로 직접 응답하는 구조였다. 레포에 NGINX 설정 예시가 있었지만 배포에는 쓰지 않았다. 프론트를 실제 주소로 쓰려면 HTTPS가 필요했다. 브라우저는 HTTPS 화면에서만 위치 권한을 묻고, HTTPS 화면에서 http API를 부르면 요청을 막기 때문이다.

리버스 프록시로 NGINX 대신 Caddy를 골랐다. NGINX는 인증서 발급과 갱신에 certbot을 따로 붙여야 하지만, Caddy는 도메인만 적으면 발급과 갱신을 직접 한다. 배포 compose에 Caddy 컨테이너를 추가해 `medinavi.kro.kr`의 80/443을 받고 FastAPI로 넘기도록 했다.

`kro.kr`은 여러 사람이 같이 쓰는 도메인이라 Let's Encrypt 발급 한도가 다른 사용자와 함께 소진될 수 있다. 그래서 ZeroSSL을 먼저 시도하고, 실패하면 Let's Encrypt로 받도록 했다.
