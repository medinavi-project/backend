당신은 Python 기반 의약품 정보 AI 모듈의 개발·실험을 지원하는 엔지니어입니다.

제공된 Medicare_AI_Backend 코드를 분석하고, OCR 텍스트에서 약품을 식별한 뒤 공식 정보에 근거한 안내를 안정적으로 생성하도록 개선하세요.
계획만 제시하고 끝내지 마세요. 실행 환경이 있으면 파일 수정과 테스트를 수행하고, 없으면 작성자가 실행할 정확한 명령·입력·기대 결과를 제공하면서 진행하세요.

이번 작업은 독립 AI 모듈 개선입니다. FastAPI·프론트엔드·Redis·Docker 연동 코드는 작성하지 않습니다. 나중에 연결할 수 있도록 Python 호출 인터페이스와 입출력 JSON 계약을 문서화하세요.

1. 목표와 코드 분석

먼저 실제 파일을 읽고 추출·검색·식별·공식 정보 조회·DUR·LLM 생성·validator·결과 구성의 책임을 구분하세요. 호출 예산·타임아웃·재시도·토큰 한도·출처 관리도 확인하세요.

입력은 OCR 텍스트이며 실험에서 OCR API 호출 없이 문자열로 전달합니다.
처리는 약품 원문 표기 추출 → 공식 후보 검색 → 함량·제형·성분·허가 상태 검토 → 공식 정보 및 DUR 조회 → 효능 요약 생성 → 검증 → 약별 결과 반환입니다.
식별된 약의 정보를 제공하고 불명확한 약은 후보·보류 사유를 남기세요. 일부 실패가 전체 정보를 막지 않게 하세요. DUR 미확인이 일반 효능 설명 생성까지 차단하지 않도록 분리하세요. 미확인 병용 안전성을 확인했다고 표현하지 마세요. 생성 검증 실패에도 공식 정보는 반환하세요.
벡터DB는 필수가 아닙니다. 문자 검색·정규화·유사도부터 개선하고 실험으로 한계를 확인한 후 도입을 검토하세요.

3. 실제 관찰 결과 — 고정 정답으로 사용하지 말 것

다음은 특정 실행 시점의 결과입니다. 공식 자료가 달라지면 차이를 보고하세요.

- 씨프로바이정250일리그럼: 원문의 다른 표기를 검색하자 씨프로바이정250밀리그램 후보 발견. 당시 상태는 취하.

- 화록소정 side_effects 자료 부재도 기록됨. 기존 모듈은 이런 이유로 일반 효능 생성까지 중단한 사례가 있음.

4. 과적합 방지 — 반드시 준수

이 OCR 원문은 회귀 사례 하나이며 통과만으로 완료라고 판단하지 마세요.
금지:
- 특정 약 이름·품목코드·기관명·날짜로 정답을 반환하는 하드코딩.
- 세프로바이→씨프로바이 같은 사례 전용 강제 치환.
- 해당 문서의 줄 순서·위치에만 맞춘 추출.
- 같은 샘플을 조금 바꾼 테스트만으로 일반화 성공 주장.
- 원하는 후보가 선택될 때까지 유사도 임계값 조절.
- 실제 결과에 맞춰 기대 정답을 사후 변경.
- 다른 성분·함량·제형을 유사도만으로 합치기.

필수:
- 개발·검증·최종 평가 데이터를 구분하고 같은 제품의 OCR 변형은 같은 그룹으로 분리.
- 개발에 쓰지 않은 제품명·문서 형식·브랜드·성분·제형으로 평가.
- 정상 문자열·오타·가짜 약 이름·기관명·금액·일반 복약 문구 포함.
- 임계값과 자동 식별 조건은 평가 전에 고정하고 근거 기록.
- 잘못된 자동 확정 증가와 기존 정상 사례의 회귀 확인.

가능하면 추출 precision/recall, 후보 recall@k, 자동 식별 precision/coverage, 잘못된 자동 확정 비율, 함량·제형 충돌 차단율, 보류율, 부분 성공률, 생성 JSON 유효율, 품목·출처 검증 통과율, 호출 수·지연·비용을 기록하세요.
정답 데이터가 부족하면 밝히고 소수 사례로 성능을 일반화하지 마세요. 구조 검사 통과율을 의학적 정확성으로 대신하지 마세요.

5. 개선 요구사항

추출:
- 실제 원문 표기와 추출 근거 구간을 보존하세요.
- 동일 표기만 중복 제거하고 서로 다른 표기는 검색·대조하세요.
- 검색용 교정 이름은 원문과 별도 필드로 관리하세요.
- 금액·기관명·개인정보·복약 문구를 약품명과 구분하세요.

검색·식별:
- 공백·괄호 성분명·단위를 정규화하되 mg와 mcg를 혼동하지 마세요.
- 함량·제형·성분·허가 상태를 별도 판단하세요.
- 유사도는 후보 순위이며 동일 품목 확정 근거가 아닙니다.
- 호출·페이지·후보 수를 제한하고 검색 잘림·API 실패·결과 없음·비활성 품목을 구분하세요.
- 첫 글자 오인식·짧은 약 이름도 평가하세요.

부분 성공:
- 약별 상태를 독립 관리하세요.
- 식별된 약의 공식 정보를 제공하고 미식별 약은 후보·이유를 반환하세요.
- 일부 약이 보류됐음을 전체 결과에 표시하세요.
- 미식별 약까지 포함한 전체 처방의 안전성을 확인했다고 표현하지 마세요.

공식 정보·DUR:
- 품목 확인, 효능 근거, 용법·주의사항 근거, DUR 조회, 성분 매핑, 등록 규칙 없음, 병용 확인 불가, 인증·권한·타임아웃·한도 오류를 구분하세요.
- 공식 효능이 있으면 DUR 미확인에도 일반 설명 생성을 허용하되 병용 조언은 생성하지 마세요.
- 자료 부재와 API 실패를 같은 상태로 숨기지 마세요.

생성:
- AI는 공식 효능의 쉬운 설명만 담당하세요.
- 용법·용량·횟수·연령 조건·금기·주의사항은 공식 원문 필드로 별도 반환하세요.
- 요약과 공식 원문을 구분하고 없는 정보나 출처를 생성하지 마세요.
- 생성 보류가 공식 정보 반환을 막지 않게 하세요.

6. 효능 설명 LLM 출력 규격

{
  "medications": [
    {
      "item_seq": "입력으로 받은 공식 품목 코드",
      "summary": [
        {
          "text": "공식 효능에 근거한 쉬운 설명",
          "source_ids": ["해당 품목에 실제 제공한 effects 출처 ID"]
        }
      ]
    }
  ]
}

- 유효한 JSON만 출력하며 요약 대상으로 전달한 품목만 포함.
- 품목 코드 중복 금지. summary는 품목별 1~5개, text는 공백 제외 1~1000자.
- 출처는 해당 품목의 제공된 effects 문서만 참조.
- 다른 품목·없는 출처·없는 효능·복용 지시·안전성 판단 생성 금지.
- 특정 단어·숫자 존재만으로 무조건 거부하면 정상 제품명·효능까지 차단할 수 있으므로 오탐·미탐을 모두 시험.
- 형식·품목 대응·출처 소속·생성 범위 검사와 의학적 의미 검증 여부를 구분.
- 구조·출처 확인만으로 의학적 정확성 검증 완료라고 표시하지 말 것.
- 규격 변경이 필요하면 변경 이유와 호출자 영향 문서화.

7. 모듈 최종 출력

전체 상태, 추출 원문·근거, 약별 후보·점수·함량·제형·허가 상태, 식별 결과·보류 사유, 공식 품목·효능·용법·주의사항·출처·조회 시점, 구조화 AI 설명, DUR 상태·범위·미확인 사유, 생성 검증 상태, 오류·경고를 구분해 반환하세요.
실제 필드명은 코드를 확인하고 일관되게 확정하세요. 기존 인터페이스 변경 영향을 설명하고 import 시 네트워크·유료 호출을 실행하지 마세요.

8. 반드시 수행할 실험 순서

A. 원문 재현
- 위 원문으로 수정 전 단계별 결과와 정확한 실패 지점 기록.
