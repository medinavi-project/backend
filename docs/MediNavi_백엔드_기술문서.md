# MediNavi 백엔드 기술문서

Nov 26, 2026 · 백엔드(김건우)

「MediNavi 기술문서」(프론트)와 같은 장 구성으로 백엔드 내용을 정리했습니다. 모든 수치와 설정은 2026-11-26 기준 코드(`MediNavi_BE`)에서 확인한 값입니다. 프론트 기술문서와 다른 부분은 [10장](#10-프론트-기술문서와-맞춰야-할-부분)에 따로 모았습니다.

## 1. 백엔드가 맡는 일

화면은 서버 응답을 보여 주기만 합니다. 질문 만들기, 응급 판단, 근거 검색, 분석, 병원 선별, 약 식별은 모두 백엔드가 합니다.

| 기능 | 백엔드가 하는 일 |
| --- | --- |
| F1. 문진 | 응급 규칙 검사 → LLM으로 증상 슬롯 채우기 → 다음 질문 결정 → MedlinePlus FAISS 검색(RAG) → 근거 기반 분석 → 진료과 표준화 |
| F2. 병원 | 좌표 → 행정구역(역지오코딩) → 진료과·지역별 공공데이터 조회(1시간 캐시) → 거리·진료 중 계산 → 진료 중 먼저 정렬 |
| F3. 복약 | OCR → 약 이름 후보 → 식약처 허가 목록(42,725개)과 대조 → 공식 정보 조회 → 쉬운 설명 → 음성 주소 발급 |

## 4. 아키텍처

```
[브라우저 React SPA]
        │ HTTPS medinavi.kro.kr
        ▼
┌──────────── NCP Server · Docker Compose ────────────┐
│  Caddy (80/443, 인증서 자동)                         │
│    ▼ HTTP :8000 (컨테이너 내부)                       │
│  Uvicorn ─ FastAPI                                  │
│    ├─ 문진 ── Redis (세션 30분)                      │
│    │    └─ FAISS 인덱스 (MedlinePlus 1,017건, 메모리) │
│    ├─ 병원 ── 메모리 캐시 (진료과·지역별 1시간)        │
│    └─ 복약 ── 약 이름 사전 (42,725개, 메모리)          │
│               Redis (음성 문장 1시간) + mp3 메모리 캐시 │
└─────────────────────────────────────────────────────┘
        │
        ▼ 외부 API
 CLOVA Studio(HCX-005, bge-m3) · CLOVA OCR · CLOVA Voice · NCP Reverse Geocoding
 국립중앙의료원 병·의원 API · 식약처 의약품 API · MedlinePlus(인덱스 생성, 장애 시 대체 검색)

[배치·배포]
 로컬: MedlinePlus XML → bge-m3 임베딩 → FAISS 인덱스 → git
 로컬: 식약처 수집기 → 약 이름 사전 → git
 GitHub Actions → GHCR 이미지 → SSH로 서버에서 docker compose up
```

- **DB는 쓰지 않습니다.** 바뀌는 데이터는 30분짜리 문진 세션뿐이라 Redis TTL로 충분합니다. FAISS 인덱스와 약 이름 사전은 배포할 때만 바뀌는 읽기 전용 데이터라서, 이미지에 넣어 메모리에 올리는 편이 빠르고 운영할 구성 요소도 적습니다.
- **리버스 프록시는 NGINX가 아니라 Caddy입니다.** 도메인만 적으면 인증서 발급·갱신을 직접 해서 certbot 같은 별도 구성이 필요 없습니다. kro.kr은 여러 사람이 같이 쓰는 도메인이라 Let's Encrypt 한도가 차 있을 수 있어 ZeroSSL을 먼저 씁니다.

### 4-1. API (6개 + 상태 확인)

| 메서드·경로 | 하는 일 | 성공 |
| --- | --- | --- |
| `POST /api/v1/chat/sessions` | 첫 증상으로 문진 시작, 응급이면 바로 `EMERGENCY` | 201 |
| `POST /api/v1/chat/sessions/{id}/messages` | 답 처리, 다음 질문 또는 완료 | 200 |
| `GET /api/v1/chat/sessions/{id}/result` | 저장된 결과 조회 (재분석 없음) | 200 |
| `GET /api/v1/hospitals/open` | 진료과(쉼표로 최대 5개)·좌표·반경으로 병원 검색 | 200 |
| `POST /api/v1/medications/scan` | 사진 한 장 → 약 설명 카드 | 200 |
| `GET /api/v1/medications/audio/{audio_id}` | 약 안내 mp3 | 200 |
| `GET /health` | API·Redis·AI 키·OCR·음성 설정 확인 | 200 |

요청·응답 JSON과 에러 코드는 「MediNavi API 명세서 v1.1」을 원본으로 합니다.

## 5. 데이터 및 AI 활용

### 5-1. 문진 처리 순서 (한 턴)

1. **응급 규칙 검사 (LLM 호출 전)**: 키워드 규칙으로 위험 신호를 찾습니다. 걸리면 LLM을 부르지 않고 바로 `EMERGENCY`를 돌려줍니다.
2. **슬롯 채우기 (HCX-005)**: 답에서 증상 항목을 뽑습니다. LLM이 놓친 값은 규칙으로 보완합니다(예: "7" → 직전 질문이 강도면 severity 7, "오른쪽 아래" → 오른쪽 아랫배).
3. **끝낼지 결정 (서버)**: LLM이 `COMPLETE`라고 해도 서버가 다시 판단합니다.
   - 7번째 답이면 끝냅니다.
   - 핵심 슬롯이 비어 있으면 계속 묻습니다.
   - 넓은 부위("배", "머리")면 상세 위치를 한 번 더 묻습니다.
   - 나이에 따라 진료과가 달라지는 증상(기침·발열·콧물·설사·구토·복통)이면 나이를 한 번 묻습니다.
4. **다음 질문 검증 (서버)**: LLM 질문이 이미 채운 슬롯이나 이 증상에 필요 없는 슬롯을 묻거나, 질문 문장이 아니면 서버의 기본 질문으로 바꿉니다.
5. **완료 시 RAG + 분석**: 5-2 참고.

**증상별 필수 슬롯**

| 주증상 종류 | 묻는 슬롯 |
| --- | --- |
| 통증 ("아프", "통", "쑤시" 등) | 주증상, 부위, 시작 시점, 강도(0~10), 동반 증상 |
| 전신 증상 (기침, 발열, 콧물, 어지러움 등) | 주증상, 시작 시점, 동반 증상 |
| 그 밖 (발진 등) | 주증상, 부위, 시작 시점, 동반 증상 |

`region`(지역) 슬롯은 묻지 않습니다. 사용자가 먼저 말한 경우에만 저장합니다. 병원 검색은 화면이 보내는 좌표를 쓰기 때문에 문진의 지역 값은 쓰지 않습니다.

### 5-2. RAG (근거 검색 → 근거 기반 분석)

| 단계 | 방식 |
| --- | --- |
| 문서 준비 (사전) | MedlinePlus 공식 XML의 영문 Health Topic 1,017건. 문서 1건 = 제목 + 요약 앞 900자 = 벡터 1개 (청크 분할 없음) |
| 임베딩 | CLOVA Studio `bge-m3`, 벡터를 정규화한 뒤 FAISS `IndexFlatIP`에 저장 (내적 = 코사인 유사도) |
| 질의 | 한국어 증상 요약 + HCX-005가 만든 영어 의학 검색어 3개를 합쳐 임베딩 1회 |
| 선택 기준 | 코사인 유사도 상위 3개. 리랭커는 쓰지 않음 |
| 분석 | 3개 문서의 제목·요약을 프롬프트 근거로 넣어 HCX-005가 의심 질환(최대 3개)·이유·추천 진료과를 JSON으로 작성 |
| 출처 | 고른 문서를 `references`로 반환 (제목은 한국어로 번역) |
| 장애 대비 | 인덱스가 없거나 검색이 실패하면 MedlinePlus 실시간 검색 + 임베딩 순위로 자동 전환 |

검색 예 (실제 실행, 괄호는 유사도):

| 증상 | 1위 | 2~3위 |
| --- | --- | --- |
| 오른쪽 아랫배 통증, 발열 | Appendicitis (0.72) | Indigestion, Intestinal Obstruction |
| 관자놀이 두통 | Migraine (0.66) | Headache, Meningitis |
| 기침, 콧물 | Common Cold (0.68) | Cough, Cold and Cough Medicines |

### 5-3. LLM 응답 규격과 검증

문진 LLM(HCX-005)은 매 턴 같은 JSON을 내도록 프롬프트로 고정하고, 서버가 검증합니다.

- `action`: `ASK_FOLLOW_UP` 또는 `COMPLETE`. `EMERGENCY`는 LLM이 아니라 서버 규칙이 정합니다.
- `symptom_updates`: 이번 답에서 확인한 항목만. 5개 슬롯과 참고용 `region`
- `next_question`: 질문 하나 (끝이면 `null`)
- `analysis`: 끝낼 때만. `assessment_status`(`PRELIMINARY`·`INSUFFICIENT_INFORMATION`·`INSUFFICIENT_EVIDENCE`), 증상 요약, 의심 질환 0~3개, 추천 진료과

**검증 단계**: 코드 블록 제거와 JSON 추출 → 필드·길이·타입 검사(엔진) → Pydantic 스키마 검사(백엔드) → 실패하면 `AI_RESPONSE_INVALID`로 처리하고 세션을 `FAILED`로 바꿉니다. Structured Outputs 기능은 쓰지 않고, 프롬프트와 서버 검증으로 형식을 지킵니다.

**할루시네이션 방지 (서버 처리)**

- 추천 진료과는 표준 19종 이름으로만 내보냅니다(예: 소화기내과 → 내과). 병원 검색에 그대로 쓸 수 있습니다.
- 의심 질환의 "이유" 문장에 사용자가 말하지 않은 증상(공복·야간·출혈·발열 등)이 나오면 그 문장을 지웁니다. 참고 문서의 증상을 사용자 증상처럼 쓰는 것을 막기 위해서입니다.
- 근거 문서가 증상과 맞지 않으면 `INSUFFICIENT_EVIDENCE`로 질환을 비웁니다.

### 5-4. 응급 판단

LLM이 아니라 **키워드 규칙**으로 판단합니다. 매 턴 LLM보다 먼저 검사합니다.

| 규칙 | 예시 표현 |
| --- | --- |
| 흉통 | "흉통", "가슴" + "조이/아파/짓눌" |
| 호흡곤란 | "숨이 차", "숨쉬기 힘", "숨이 막" |
| 의식저하 | "기절", "실신", "쓰러졌" |
| 뇌졸중 의심 | "마비", "말이 어눌", "입이 돌아", "한쪽 팔" |
| 대량 출혈 | "피를 토", "토혈", "피가 멈추지" |
| 경련 | "경련", "발작" |
| 극심한 두통 | "벼락", "생애 최악" |
| 아나필락시스 의심 | "아나필락시스", "목·입술·혀가 붓" + "숨/호흡" |
| 자해 위험 | "죽고 싶", "자살", "자해" → 109 안내 |
| 응급 질환 의심 | "뇌졸중 온 것 같아요"처럼 응급 질환명을 의심하는 말 (`conditions.csv`, 진단받았다는 말은 제외) |

부정 표현("가슴은 안 아파요")도 응급으로 잡습니다. 응급을 놓치는 것보다 낫다고 보고 의도적으로 보수적으로 둔 것이고, 목록은 의료 자문 검토 대상입니다.

### 5-5. 약 이름 식별 (OCR → 공식 품목)

1. CLOVA OCR 글자에서 약 이름 후보를 뽑습니다.
2. 공백·단위·괄호 표기를 정규화합니다.
3. 약 이름 사전 42,725개에서 rapidfuzz 문자 유사도로 후보를 찾습니다(66점 이상).
4. **확정 기준**
   - 공식 이름과 정확히 같으면 확정합니다.
   - 오타 추정은 1위가 75점 이상이고 2위보다 15점 이상 높으며, 함량·제형이 충돌하지 않을 때만 인정합니다.
   - 봉투의 효능 문구(예: "항생제")가 공식 효능과 맞는지, 허가 취하·만료 상태인지도 확인합니다.
5. 애매하면 확정하지 않고 `uncertain_medications`로 보냅니다. 오타로 추정한 약에는 `warning`을 붙입니다.

유사도는 문자 비교 점수일 뿐 그 약일 확률이 아니라서, 유사도만으로는 품목을 확정하지 않습니다.

### 5-6. 복약 설명과 음성

- 식약처 원문의 HTML을 일반 글자로 바꿉니다(줄바꿈은 `\n`). 효능과 주의사항은 HCX-005로 쉬운 말로 다시 쓰고, 실패하면 원문을 그대로 둡니다.
- 설명은 5개 항목(`purpose`, `how_to_take`, `precautions`, `side_effects`, `storage`)으로 나눕니다.
- **음성**: 스캔 응답에는 주소만 넣고, 재생할 때 CLOVA Voice로 mp3를 만듭니다. 읽을 문장은 Redis에 1시간 저장하고, 같은 문장은 서버 메모리의 mp3를 다시 씁니다. 주소에는 무작위 ID만 들어가므로 아무 문장이나 읽게 하는 데 악용할 수 없습니다. 읽는 내용은 약 이름과 효능뿐입니다(허가 용법은 실제 처방과 다를 수 있음).

### 5-7. 병원 검색

1. 좌표와 반경 위 8방향 점을 역지오코딩해 검색 반경이 걸치는 시·군·구를 모두 모읍니다. 공공데이터 API가 시·군·구 단위로만 조회되기 때문입니다.
2. 진료과 × 지역 조합을 병렬로 조회합니다. 각 조회 결과는 1시간 캐시합니다.
3. 반경 밖을 빼고 거리를 계산합니다. 진료 중인지는 요일별 진료시간과 현재 한국 시각으로 서버가 계산합니다(밤샘 진료 포함).
4. 진료과마다 "진료 중 먼저, 그다음 가까운 순"으로 최대 20곳을 고른 뒤 합칩니다. 같은 병원은 한 번만 넣고 `departments`에 진료과를 모읍니다.

### 설계 결정과 이유

| 결정 | 이유 |
| --- | --- |
| DB 대신 Redis + 메모리 적재 | 바뀌는 데이터는 30분 세션뿐. 문서·약 이름은 배포할 때만 바뀌는 읽기 전용 데이터라 메모리가 가장 빠르고 단순함 |
| FAISS (pgvector 대신) | 문서 1,017건, 4MB라 파일 하나로 충분. 수십만 건이거나 실시간으로 문서를 추가하게 되면 pgvector로 옮김 (검색 함수 하나만 교체) |
| 인덱스는 로컬에서 만들어 이미지에 포함 | 서버에서 만들면 배포할 때마다 사라짐. 어디서 만들어도 같은 결과 |
| 응급은 규칙으로 | LLM 판단은 매번 다를 수 있고 느림. 응급은 놓치면 안 되므로 LLM보다 먼저, 보수적으로 |
| 문진 종료는 서버가 결정 | LLM이 핵심 정보 없이 끝내는 문제를 막기 위해 |
| 기능별 API 키 분리 | 한도·장애가 다른 기능으로 번지지 않게, 사용량을 기능별로 보기 위해 |
| Caddy (NGINX 대신) | 인증서 발급·갱신이 자동이라 서버에서 손으로 할 일이 없음. 이 규모에서는 성능 차이가 없음 |
| 음성은 재생할 때 생성 | 스캔 속도를 그대로 두고, 듣지 않는 음성은 만들지 않음 |
| hosAI 엔진을 거의 그대로 두고 어댑터로 연결 | 팀원이 엔진을 고치면 파일만 교체할 수 있게 |
