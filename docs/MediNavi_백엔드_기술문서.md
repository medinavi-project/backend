## 1. 백엔드가 맡는 일

프론트는 서버 응답을 표시하고, 질문 생성·응급 판단·근거 검색·분석·병원 선별·약 식별은 모두 백엔드에서 처리합니다.

| 기능 | 백엔드가 하는 일 |
| --- | --- |
| F1. 문진 | 응급 규칙 검사 → LLM으로 증상 슬롯 채우기 → 다음 질문 결정 (반복) → 서버가 문진 완성 판단 → MedlinePlus FAISS 검색(RAG) → 근거 기반 분석 → 진료과 표준화 |
| F2. 병원 | 좌표를 시·군·구 이름으로 변환해 반경이 걸치는 지역 수집(역지오코딩) → 진료과 × 지역 병렬 조회 → 반경·진료 중 판정 → 진료과별 진료 중 먼저 20곳 → 중복 병원 합치기 |
| F3. 복약 | OCR → 약 이름 후보 추출 → 식약처 허가 목록 기반 약 이름 사전(42,725개)과 글자 유사도로 대조 → 함량·제형·효능 단서로 품목 확정(좁혀지지 않으면 보류) → 공식 정보 조회 → 원문 범위 안에서 쉬운 말로 가공 → 음성 주소 발급 |

## 4. 아키텍처

```
[브라우저 React SPA]
        │ HTTPS medinavi.kro.kr
        ▼
┌──────────── NCP Server · Docker Compose ────────────┐
│  Caddy (80/443, 인증서 자동)                         │
│    ├─ /, /chat, /hospitals … ──▶ NCP Global Edge     │
│    │      (프론트 빌드 파일, Object Storage)          │
│    ▼ /api, /health, /docs → HTTP :8000               │
│  Uvicorn ─ FastAPI                                  │
│    ├─ 문진 ── Redis (세션 30분)                      │
│    │    └─ FAISS 인덱스 (MedlinePlus 1,017건, 메모리) │
│    ├─ 병원 ── 메모리 캐시 (진료과·지역별 1시간)        │
│    └─ 복약 ── 약 이름 사전 (42,725개, 메모리)          │
│               Redis (음성 문장 1시간) + mp3 메모리 캐시 │
└─────────────────────────────────────────────────────┘
        │
        ▼ 외부 API
 CLOVA Studio(HCX-005, bge-m3) · CLOVA OCR · CLOVA Voice · NCP Reverse Geocoding
 국립중앙의료원 병·의원 API · 식약처 의약품 API · MedlinePlus(인덱스 생성, 장애 시 대체 검색)

[배치·배포]
 로컬: MedlinePlus XML → bge-m3 임베딩 → FAISS 인덱스 → git
 로컬: 식약처 수집기 → 약 이름 사전 → git
 GitHub Actions → GHCR 이미지 → SSH로 서버에서 docker compose up
```

- **DB는 쓰지 않습니다.** 증상(민감 정보)은 영구 저장하지 않고 Redis에 30분만 둔 뒤 자동 삭제합니다. FAISS 인덱스와 약 이름 사전은 배포할 때만 바뀌는 읽기 전용 데이터라서, 이미지에 넣어 메모리에 올리는 편이 빠르고 운영할 구성 요소도 적습니다.
- **화면과 API를 한 주소로 묶었습니다.** 프론트는 NCP Object Storage + Global Edge에 따로 배포하고, Caddy가 화면 주소는 엣지로, API는 FastAPI로 나눠 보냅니다. 화면과 API가 같은 주소라 CORS 설정이 필요 없고, 확장자 없는 화면 주소는 `index.html`로 재작성해 새로고침 시에도 화면이 정상 표시됩니다.
- **리버스 프록시는 Caddy를 씁니다.** 도메인 설정만으로 인증서 발급·갱신을 자동 처리해 certbot 등 별도 구성이 불필요합니다. kro.kr은 공유 도메인이라 Let's Encrypt 발급 한도에 도달할 수 있어 ZeroSSL을 우선 사용합니다.

### 4-1. API (6개 + 상태 확인)

| 메서드·경로 | 하는 일 | 성공 |
| --- | --- | --- |

## 5. 데이터 및 AI 활용

### 5-1. 문진 처리 순서 (한 턴)

1. **응급 규칙 검사 (LLM 호출 전)**: 키워드 규칙으로 위험 신호를 찾습니다. 해당하면 LLM을 호출하지 않고 즉시 `EMERGENCY`를 반환합니다.
2. **증상 슬롯 채우기 (HCX-005 + 서버 검증)**: LLM이 사용자 답변에서 주증상·부위·발생 시점·강도·동반 증상 값을 뽑아, 정해진 JSON 형식(`symptom_updates`)으로 돌려줍니다. 서버는 JSON 형식과 허용된 필드인지 검증한 뒤 세션 상태에 합칩니다. LLM이 놓친 값은 직전 질문을 보고 규칙으로 보완합니다(예: 강도를 물었는데 "7"이라고 답하면 severity 7, "오른쪽 아래"라고 답하면 오른쪽 아랫배).
3. **문진 완성 판단 (서버)**: 문진 종료는 LLM이 아니라 서버가 정합니다. LLM이 `COMPLETE`를 보내도, 증상 종류별 필수 슬롯(아래 표)이 다 찼는지 서버가 다시 확인합니다.
   - 완성 조건: 증상 종류별 필수 슬롯이 모두 채워지면 완성. 다 채워지지 않아도 최대 7턴에서 완성 처리해 질문 횟수를 제한.
   - 필수 슬롯이 비어 있으면: LLM이 COMPLETE를 보내도 빈 슬롯을 이어서 질문.
   - 부위가 넓게 답해진 경우("배", "머리"): 진료과 판단을 위해 상세 위치를 한 번 더 질문.
   - 나이에 따라 진료과가 갈리는 증상(기침·발열·콧물·설사·구토·복통): 소아과 여부 판단을 위해 나이를 한 번 질문.
4. **다음 질문 검증 (서버)**: LLM 질문이 이미 채운 슬롯이나 이 증상에 필요 없는 슬롯을 묻거나, 질문 문장이 아니면 서버의 기본 질문으로 바꿉니다.
5. **완료 시 RAG + 분석**: 대화 중에는 RAG를 쓰지 않습니다. 다중 턴으로 증상 JSON 규격이 완성되면, 그 최종 데이터로 마지막에 한 번만 검색하고 분석합니다(5-2 참고).

**증상별 필수 슬롯**

| 주증상 종류 | 묻는 슬롯 |
| --- | --- |
| 통증 ("아프", "통", "쑤시" 등) | 주증상, 부위, 시작 시점, 강도(0~10), 동반 증상 |
| 전신 증상 (기침, 발열, 콧물, 어지러움 등) | 주증상, 시작 시점, 동반 증상 |
| 그 밖 (발진 등) | 주증상, 부위, 시작 시점, 동반 증상 |

`region`(지역) 슬롯은 묻지 않습니다. 사용자가 먼저 말한 경우에만 저장합니다. 병원 검색은 화면이 보내는 좌표를 쓰기 때문에 문진의 지역 값은 쓰지 않습니다.

### 5-2. RAG (근거 검색 → 근거 기반 분석)

| 단계 | 방식 |
| --- | --- |
| 문서 준비 (사전) | MedlinePlus 공식 XML의 영문 Health Topic 1,017건. 문서 1건 = 제목 + 요약 앞 900자 = 벡터 1개 (청크 분할 없음) |
| 임베딩 | CLOVA Studio `bge-m3`, 벡터를 정규화한 뒤 FAISS `IndexFlatIP`에 저장 (내적 = 코사인 유사도) |
| 질의 | 완성된 증상 슬롯으로 만든 한국어 요약 + HCX-005가 만든 영어 의학 검색어 3개를 합쳐 임베딩 1회 |
| 선택 기준 | 코사인 유사도 상위 3개. 리랭커는 쓰지 않음 |
| 분석 | 3개 문서의 제목·요약을 프롬프트 근거로 넣어 HCX-005가 의심 질환(최대 3개)·이유를 작성. 추천 진료과는 문서 근거가 아니라 LLM 판단이며, 서버가 표준 19종으로 정규화하고, 목록 밖이면 의심 질환 → 사용자가 말한 질환 → 증상 키워드 순으로 대응표에서 진료과 결정. 검색된 문서가 없으면 `INSUFFICIENT_EVIDENCE`로 의심 질환을 비우고, 필수 정보가 부족하면 `INSUFFICIENT_INFORMATION`으로 분석하지 않음 |
| 출처 | 고른 문서를 `references`로 반환 (제목은 한국어로 번역) |
| 장애 대비 | 인덱스가 없거나 검색이 실패하면 MedlinePlus 실시간 검색으로 자동 전환하고, 결과를 임베딩 유사도로 다시 정렬해 상위 3개 사용 |

검색 예 (실제 실행, 괄호는 유사도):

| 증상 | 1위 | 2~3위 |
| --- | --- | --- |
| 오른쪽 아랫배 통증, 발열 | Appendicitis (0.72) | Indigestion, Intestinal Obstruction |
| 관자놀이 두통 | Migraine (0.66) | Headache, Meningitis |
| 기침, 콧물 | Common Cold (0.68) | Cough, Cold and Cough Medicines |

### 5-3. LLM 응답 규격과 검증

문진 LLM(HCX-005)은 매 턴 같은 JSON을 내도록 프롬프트로 고정하고, 서버가 검증합니다.

- `action`: `ASK_FOLLOW_UP` 또는 `COMPLETE`. `EMERGENCY`는 LLM이 아니라 서버 규칙이 정합니다.
- `symptom_updates`: 이번 답에서 확인한 항목만. 5개 슬롯과 참고용 `region`
- `next_question`: 질문 하나 (끝이면 `null`)
- `analysis`: 끝낼 때만. `assessment_status`(`PRELIMINARY`·`INSUFFICIENT_INFORMATION`·`INSUFFICIENT_EVIDENCE`), 증상 요약, 의심 질환 0~3개, 추천 진료과

**검증 단계**: 코드 블록 제거와 JSON 추출 → 필드·길이·타입 검사(엔진) → Pydantic 스키마 검사(백엔드) → 실패하면 `AI_RESPONSE_INVALID`로 처리하고 세션을 `FAILED`로 바꿉니다. Structured Outputs 기능은 쓰지 않고, 프롬프트와 서버 검증으로 형식을 지킵니다.

**할루시네이션 방지 (서버 처리)**

- 추천 진료과는 표준 19종 이름으로만 내보냅니다(예: 소화기내과 → 내과). 병원 검색에 그대로 쓸 수 있습니다.
- 의심 질환의 "이유" 문장에 사용자가 말하지 않은 증상(공복·야간·출혈·발열 등)이 나오면 그 문장을 지웁니다. 참고 문서의 증상을 사용자 증상처럼 쓰는 것을 막기 위해서입니다.
- 근거 문서가 검색되지 않으면 `INSUFFICIENT_EVIDENCE`로 질환을 비웁니다.

### 5-4. 응급 판단

LLM이 아니라 **키워드 규칙**으로 판단합니다. 매 턴 LLM보다 먼저 검사합니다.

| 규칙 | 예시 표현 |
| --- | --- |
| 흉통 | "흉통", "가슴" + "조이/아파/짓눌" |
| 호흡곤란 | "숨이 차", "숨쉬기 힘", "숨이 막" |
| 의식저하 | "기절", "실신", "쓰러졌" |
| 뇌졸중 의심 | "마비", "말이 어눌", "입이 돌아", "한쪽 팔" |
| 대량 출혈 | "피를 토", "토혈", "피가 멈추지" |
| 경련 | "경련", "발작" |
| 극심한 두통 | "벼락", "생애 최악" |
| 아나필락시스 의심 | "아나필락시스", "목·입술·혀가 붓" + "숨/호흡" |
| 자해 위험 | "죽고 싶", "자살", "자해" → 109 안내 |
| 응급 질환 의심 | "뇌졸중 온 것 같아요"처럼 응급 질환명을 의심하는 말 (`conditions.csv`, 진단받았다는 말은 제외) |

부정 표현("가슴은 안 아파요")도 응급으로 판정합니다. 응급 누락을 막기 위해 의도적으로 보수적인 기준을 적용했으며, 목록은 의료 자문 검토 대상입니다.

### 5-5. 약 이름 식별 (OCR → 공식 품목)

1. CLOVA OCR 글자에서 약 이름 후보를 뽑습니다.
2. 공백·단위·괄호 표기를 정규화합니다.
3. 약 이름 사전 42,725개에서 rapidfuzz 글자 유사도로 후보를 찾습니다. 66점 이상으로 1차로 거른 뒤, 80점 이상(짧은 이름은 90점)이거나 한 글자만 다른 이름만 후보로 남깁니다.
4. **확정 기준**
   - 먼저 공식 이름과 정확히 같은 품목을 찾고, 없거나 허가 취하·만료 품목이면 아래 기준으로 한 번 더 판정합니다.
   - 오타 추정은 1위가 75점 이상이고 2위보다 15점 이상 높으며, 함량·제형이 충돌하지 않을 때만 인정합니다.
   - 오타로 추정한 약과 허가 취하·만료 약은 봉투의 효능 문구(예: "항생제")가 식약처 공식 효능과 같은 분류일 때만 확정합니다. 봉투에 효능 문구가 없으면 확정하지 않습니다.
5. 후보가 하나로 좁혀지지 않으면 추측하지 않고 `uncertain_medications`("확인 필요")로 분리합니다. 오타로 추정한 약에는 `warning`을 붙입니다.

유사도는 문자 비교 점수일 뿐 그 약일 확률이 아니라서, 유사도만으로는 품목을 확정하지 않습니다.

### 5-6. 복약 설명과 음성

- 식약처 원문의 HTML 태그를 걷어 냅니다. 효능과 주의사항은 HCX-005가 원문 범위 안에서 쉬운 말로 가공하고, 가공에 실패하면 원문을 그대로 보여 줍니다.
- 설명은 5개 항목(`purpose`, `how_to_take`, `precautions`, `side_effects`, `storage`)으로 나눕니다.
- **음성 (CLOVA Voice)**
  - 생성 시점: 스캔 응답에는 음성 주소만 넣고, 사용자가 재생할 때 mp3를 생성. 듣지 않는 약은 생성하지 않음
  - 보관: 읽을 문장은 Redis에 1시간, 같은 문장의 mp3는 서버 메모리에서 재사용
  - 보안: 주소에는 무작위 ID만 들어가 임의 문장 합성에 악용 불가
  - 읽는 내용: 약 이름과 효능만. 허가 용법은 실제 처방과 다를 수 있어 제외

### 5-7. 병원 검색

1. 좌표를 시·군·구 이름으로 변환해(역지오코딩) 검색 반경이 걸치는 지역을 모두 모읍니다. 공공데이터 병원 API가 지역 단위로만 조회되기 때문입니다.
2. 진료과 × 지역 조합을 병렬로 조회합니다. 각 조회 결과는 1시간 캐시합니다.
3. 병원까지 거리를 계산해 반경 밖 병원을 뺍니다. 진료 중인지는 요일별 진료시간과 현재 한국 시각으로 서버가 계산합니다(밤샘 진료 포함).
4. 진료과마다 "진료 중 먼저, 그다음 가까운 순"으로 최대 20곳을 고른 뒤 합칩니다. 같은 병원은 한 번만 넣고 `departments`에 진료과를 모읍니다.

### 설계 결정과 이유

| 결정 | 이유 |
| --- | --- |
| DB 대신 Redis + 메모리 적재 | 증상(민감 정보)은 영구 저장하지 않고 30분 뒤 자동 삭제. 문서·약 이름은 배포 때만 바뀌는 읽기 전용이므로 DB 없이 메모리에 적재 |
| FAISS (pgvector 대신) | 1,017건·4MB이므로 파일 기반 FAISS 활용. 전체를 정확히 비교해도 1ms이고, 문서가 배포 때만 바뀌어 별도 벡터 DB 서버 불필요. 수십만 건으로 늘거나 실시간 추가가 필요하면 pgvector 검토 |
| 인덱스는 로컬에서 만들어 이미지에 포함 | 1,017건 임베딩은 호출 한도로 오래 걸려 서버 기동 때 만들기 어려움. 미리 만들어 이미지에 넣어 배포마다 같은 인덱스로 결과를 재현 |
| 응급은 규칙으로 | 키워드 규칙으로 LLM보다 먼저 판단. 놓치면 안 되는 판단이므로 결과가 항상 같은 규칙 기반으로 처리 |
| 문진 종료는 서버가 결정 | LLM이 3~4번째 답에서 핵심 정보 없이 끝내던 문제 → 필수 슬롯이 다 차거나 7번째 답일 때만 서버가 종료 |
| 기능별 API 키 분리 | 한도·장애가 다른 기능으로 번지지 않게, 사용량을 기능별로 보기 위해 |
| Caddy (NGINX 대신) | 인증서 발급·갱신이 자동이라 별도 인증서 관리 불필요. 이 규모에서는 성능 차이 없음 |
| 음성은 재생할 때 생성 | 스캔 응답 지연을 막고, 재생하지 않는 음성은 생성하지 않음 |
| hosAI 엔진을 거의 그대로 두고 어댑터로 연결 | 엔진이 수정되면 파일 교체만으로 반영 가능 |
